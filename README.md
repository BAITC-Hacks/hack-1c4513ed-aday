**EKT StockPilot** — веб-сервис для менеджера отдела закупа ТОО «Электрокомплект» (ekt.kz), который по истории продаж, остаткам, товарам в пути и минимальным партиям формирует рекомендованные заказы поставщикам с обоснованием по каждой позиции.

Кейс HackAlem AI, трек «Логистика»: *Автоматический расчёт заказов поставщикам для пополнения склада*.

## 1. Проблема и для кого решение

Сейчас потребность в пополнении склада считается вручную в Excel. Это долго, поэтому расчёт делается редко. В результате по одним позициям копятся излишки, по другим возникает дефицит, а разовые крупные отгрузки одному клиенту завышают «регулярную» потребность.

**Пользователь:** менеджер отдела закупа.
**Ценность:** меньше денег в излишних запасах, меньше дефицита и упущенных продаж, расчёт за минуты вместо часов, прозрачное обоснование каждого числа.

## 2. Что реализовано

- Загрузка и очистка выгрузок 1С по поставщикам **IEK** и **Systeme Electric** (продажи по накладным, помесячные продажи и остатки, товар в пути, MOQ/кратность, сезонность).
- Выявление и исключение **разовых крупных заказов** на уровне строк накладных.
- Оценка и компенсация **упущенного спроса** в месяцы без остатка (stockout).
- Прогноз спроса с учётом **сезонности** и **устойчивого роста/падения**.
- Расчёт **страхового запаса** в зависимости от категории товара (ABC).
- Рекомендуемое количество к заказу с учётом **остатков, товара в пути и MOQ**.
- **Срочность** по каждой позиции (критично / высокая / плановая).
- **Обоснование** по каждой строке: формульное + человеческий текст от LLM.
- **Ассистент закупщика** — чат с вопросами по рассчитанному заказу.
- Просмотр заказа **в разбивке по поставщикам**, ручная корректировка количества, **утверждение** и **экспорт в Excel/CSV** в формате, совместимом с 1С.
- Автотесты на все 5 обязательных требований кейса.

## 3. Как работает решение (основной сценарий)

1. Менеджер открывает сервис, выбирает поставщика и (опционально) категорию.
2. Нажимает **«Рассчитать»**. Сервис загружает данные, чистит их, строит прогноз и считает заказ.
3. Получает таблицу: артикул, наименование, поставщик, рекомендуемое количество, срочность, обоснование.
4. Открывает любую строку и видит расчёт по шагам и график спроса (факт / очищенный / прогноз).
5. При необходимости правит количество, задаёт вопрос ассистенту.
6. Нажимает **«Утвердить»** и выгружает заказ в Excel. **Автоматической отправки поставщику нет** — только после подтверждения сотрудником.

## 4. Методология расчёта

Все числа считает детерминированное расчётное ядро на Python. LLM **не участвует в расчёте количеств**, а только объясняет готовый результат.

### 4.1. Подготовка данных
- Приведение кодов 1С к единому виду, удаление служебных строк («Итого», многострочные заголовки).
- Отрицательные количества в накладных трактуются как возвраты.
- Текущий неполный месяц (сентябрь 2026, данные по 22.09) не используется как полный месяц истории.

### 4.2. Исключение разовых крупных заказов
В исходных данных нет ID клиента, поэтому **одна накладная рассматривается как одна покупка одного клиента**.

Для каждого артикула по строкам накладных за последние 12 месяцев считается типичный размер отгрузки (медиана) и робастный разброс (MAD). Строка считается разовой крупной, если её количество превышает порог `max(медиана + k·1.4826·MAD, m·медиана)` (TODO: указать итоговые k и m). Превышение над порогом вычитается из месячного спроса: регулярная часть остаётся, «всплеск» — нет.

Для 2024 года, где есть только помесячные данные, применяется фильтр выбросов по месячному ряду (Hampel: замена значений, отклоняющихся от скользящей медианы больше чем на 3 MAD).

### 4.3. Упущенный спрос (stockout)
Месяц считается дефицитным, если начальный остаток ≤ 0 (TODO: уточнить итоговое правило). В такие месяцы фактические продажи занижены, поэтому спрос восстанавливается как максимум из факта и типичного уровня продаж артикула в месяцы с наличием, скорректированного на сезонность.

### 4.4. Прогноз: сезонность и рост
- **Базовый уровень** — взвешенное среднее очищенного спроса за последние 6 полных месяцев без сезонности (свежие месяцы весят больше).
- **Коэффициент роста** — отношение очищенного спроса за последние 6 месяцев к тем же месяцам год назад, ограниченное диапазоном [0.7; 1.5], чтобы единичные скачки не ломали прогноз.
- **Сезонность** — индекс месяца по артикулу, если у него достаточно истории; иначе по бренду (из файлов «Сезонность»).
- Прогноз на месяц `t` = базовый уровень × рост × сезонный индекс месяца `t`.

### 4.5. Категории и страховой запас
Артикулы делятся на ABC-категории по объёму продаж за 12 месяцев (для Systeme Electric дополнительно используется категория из рабочей таблицы закупщика). От категории зависит целевой уровень сервиса:

| Категория | Уровень сервиса | z |
|---|---|---|
| A | 95% | 1.65 |
| B | 90% | 1.28 |
| C | 85% | 1.04 |

Страховой запас = `z × σ_спроса × √((L + R) / 30)`, где `σ` — стандартное отклонение очищенного месячного спроса.

### 4.6. Срок поставки
Отдельного справочника сроков нет, поэтому срок поставки `L` оценивается по файлу «Товар в пути» как разница между датой документа и плановой датой поступления (медиана по поставщику). Период пересмотра заказа `R` = 30 дней (настраивается).

### 4.7. Итоговый заказ
```
Потребность = Прогноз на (L + R) + Страховой запас
Заказ       = max(0, Потребность − Свободный остаток − Товар в пути)
Заказ       → округление вверх до MOQ / кратности
```

### 4.8. Срочность
Запас в днях = `(остаток + в пути) / среднедневной прогноз`.
- **Критично** — запаса меньше срока поставки `L` (дефицит почти неизбежен).
- **Высокая** — запаса меньше `L + 14` дней.
- **Плановая** — остальные позиции с ненулевым заказом.

## 5. Роль ИИ

- **Обоснования.** LLM получает только числа по артикулу (прогноз, остаток, в пути, исключённые всплески, восстановленный спрос, MOQ) и пишет 1–2 предложения для менеджера. Выдумывать данные запрещено промптом.
- **Ассистент закупщика.** Отвечает на вопросы по рассчитанной таблице.
- **Отказоустойчивость.** Если API недоступен, используется шаблонное объяснение, расчёт работает полностью без ИИ.
- **Приватность.** В LLM не передаются данные о клиентах и номера накладных, только агрегаты по артикулу.
- **Разработка.** Проект написан с помощью ИИ-агента OpenAI Codex.

1. Запустите приложение, выберите поставщика **IEK**, нажмите «Рассчитать».
2. Отсортируйте по срочности: вверху позиции с риском дефицита.
3. Откройте артикул **ВА47-29 (1ф) 25А IEK** (TODO: сверить): в истории есть разовая отгрузка 7 488 шт. при типичной ~12 шт. В обосновании видно, что всплеск исключён.

5. Переключитесь на **Systeme Electric**: заказ формируется отдельно по второму поставщику.
6. Выгрузите заказ в Excel.
7. В терминале в папке `hack-1c4513ed-aday` запустите `pytest -v` — тесты на 5 обязательных требований:

| Требование кейса | Тест |
|---|---|
| Все источники влияют на результат (например, рост товара в пути уменьшает заказ) | `test_all_sources_affect_order` |
| Сезонный товар получает сезонный, а не средний прогноз | `test_seasonality` |
| Stockout увеличивает расчётную потребность | `test_stockout_compensation` |
| Искусственный крупный заказ не раздувает регулярную потребность | `test_one_off_excluded` |

## 11. Ограничения

- В данных нет ID клиента и цены: разовые заказы определяются по накладной, а не по клиенту; стоимость заказа не считается.
- Нет справочника сроков поставки: срок оценён по документам «в пути».
- Остатки известны только на начало месяца, поэтому дефицит внутри месяца определяется приближённо.
- Один склад (Алматы) — расчёт по складам не разделяется.
- Длина истории транзакций ~21 месяц, поэтому годовая сезонность по артикулам оценена по двум сезонам.
- Автоотправка заказа поставщику сознательно не реализована (по требованию кейса).
